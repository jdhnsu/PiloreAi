# Code Pack Profile 路由切换 —— 手动演示测试用例

> **状态：手动演示测试推荐**
>
> 本文档用于人工验证 Code Pack 老师路由（Profile Router）的切换判断效果。
> 测试针对以下核心路由规则（见 `src/packs/code/agent-design/base-prompt.ts` 与 `src/core/router/index.ts`）：
>
> 1. 只在用户明确需要某种专门教学方式时才激活 Profile；简单事实、简短语法或直接操作问题保持 auto。
> 2. 已激活且教学方式仍匹配时保持当前 Profile；更换编程主题本身不是换 Profile 的理由。
> 3. 用户明确改换教学方式时，直接调用 `adopt_profile` 切到目标 Profile，不经过 auto。
> 4. 已激活但不再需要时，先切回 auto 再简洁回答；结束确认 + 转问简短问题是交还信号。
> 5. `@mention` 可直达指定 Profile（`@pilore` 表示交还自动路由）。

可用 Profile：`feynman`（费曼式大白话/类比）、`socrates`（苏格拉底式讲透原理）、`oris`（基础架构师/补前置路径）。

## 用例设计原则（重要）

- **避免与提示词措辞重叠**：除场景 7（机制测试）外，所有用户消息均**不复用** base prompt 与 profile description 中的"典型表达"词汇（如"太抽象/听不懂/大白话/讲透/明白了+顺便"）。用例使用语义等价的日常说法，检验的是模型的**语义路由**能力，而不是字面触发词匹配。若某场景只在全字命中触发词时才通过，说明路由仍依赖关键词而非意图判断。
- **每段只测一个变量**：激活、保持、切换、交还、直达各占独立场景，失败时可单独归因。

---

## 场景 1：正向激活 —— Feynman（语义等价，无触发词）

| 轮次 | 用户消息 |
|---|---|
| 1 | 闭包的定义我看了三遍，还是想不通这东西在真实项目里到底扮演什么角色。能不能找个我日常熟悉的事物来对应一下它？ |

**期望**：调用 `adopt_profile → feynman`，然后用类比 + 直白语言讲解，并邀请复述。

**观察点**：消息不含"抽象/听不懂/大白话/类比"等典型表达，仅靠"看了三遍还是想不通 + 想要日常事物对应"传达降低抽象度的意图；回答中不暴露 "feynman" 这个名字。

---

## 场景 2：正向激活 —— Oris（语义等价，无触发词）

| 轮次 | 用户消息 |
|---|---|
| 1 | 我想以后做后端开发，但现在连浏览器输入网址后发生了什么都不清楚，也没碰过数据库。如果目标是能独立做出一个网站，我现在该按什么步骤走？ |

**期望**：调用 `adopt_profile → oris`，给出前置知识补齐路径，而不是直接讲某个框架。

**观察点**：不应误判成 Feynman（用户没有表达"某个概念难懂"，而是暴露多层知识空白并询问路径）。消息不使用"缺哪些基础/学习顺序/从哪里开始"等原文措辞。这是 Feynman/Oris 边界的关键区分点。

---

## 场景 3：负向 —— 含陷阱词但不该激活

| 轮次 | 用户消息 | 陷阱 |
|---|---|---|
| 1 | Python 里 list 和 tuple 有什么区别？ | "区别"像 Socrates 的触发词，但这是简单事实题 |
| 2 | 我这段代码报 `IndexError` 了，帮我看看为什么？（附代码） | "为什么"像 Socrates 的触发词，但这是直接操作/调试 |

**期望**：两轮都**不调用** `adopt_profile`，直接简洁回答。

**观察点**：base prompt 明确写了"不要只按编程主题或单个触发词判断"——这段就是验证它。如果模型调了 `adopt_profile`，说明 profile description 里的反触发措辞还不够强。

---

## 场景 4：激活后保持 —— 换话题不换 profile

| 轮次 | 用户消息 |
|---|---|
| 1 | 生成器这个概念我总绕不过弯来，能不能拿个现实里的例子带我看一遍它是怎么运作的？ |
| 2 | 有点感觉了。那它跟迭代器是同一个东西吗？还是继续用刚才那种方式给我说说。 |
| 3 | 那字典存数据的时候是怎么快速找到目标的？也能这么理解吗？ |

**期望**：第 1 轮激活 feynman；第 2、3 轮**不重复调用** `adopt_profile`，继续用类比风格回答。

**观察点**：第 2、3 轮的话题连续更换（生成器→迭代器→字典哈希），但教学方式需求未变 → 必须保持。第 2 轮"继续用刚才那种方式"是延续信号而非新激活信号；若模型因话题变化而重新路由或切回 auto，就是 bug。

---

## 场景 5：激活后直接切换 —— 不经过 auto

| 轮次 | 用户消息 |
|---|---|
| 1 | 装饰器我一直没整明白，能用个好懂点的说法带我过一遍吗？ |
| 2 | 你说的那个比喻我懂了。不过现在我想深入一点：解释器执行到 `@` 这一行的时候，内部实际走了哪些步骤？我想把每一步都弄清楚。 |

**期望**：第 1 轮 `adopt_profile → feynman`；第 2 轮**直接** `adopt_profile → socrates`（不是先 auto 再 socrates）。

**观察点**：第 2 轮不使用"讲透/底层机制"等原文措辞，仅靠"内部实际走了哪些步骤/每一步都弄清楚"表达原理诉求；一个 user 消息只产生一次 `adopt_profile` 调用；切换后按苏格拉底方式（先抛引导问题）展开。

---

## 场景 6：交还信号 —— 切回 auto

| 轮次 | 用户消息 |
|---|---|
| 1 | 事件循环我完全没概念，能不能从我最熟悉的东西出发给我讲讲它？ |
| 2 | 原来是这样。再问个小问题：我就想跑一个协程，到底该调哪个函数？ |
| 3 | 那 Python 3.11 加的 `TaskGroup` 是干嘛的？一句话就行。 |

**期望**：第 2 轮"结束确认 + 转问简单 API 问题"是交还信号 → 先 `adopt_profile → auto`，再简洁回答。第 3 轮保持 auto。

**观察点**：确认词（"原来是这样"）和转问词（"再问个小问题"）均与 prompt 中列举的字样不同，测试的是对交还**意图**的识别而非字样匹配；顺序必须是"先切 auto 再回答"（同一轮内）。若第 2 轮继续用费曼风格长篇展开，说明交还信号没生效。

---

## 场景 7：@mention 直达（机制测试，允许直接指定）

| 轮次 | 用户消息 | 期望 |
|---|---|---|
| 1 | `@socrates` 讲透 Python 的 GIL，并帮我辨析"GIL 让多线程完全没用"这个说法 | 直接激活 socrates，无需模型自行判断 |
| 2 | `@pilore` 顺便问下，`sys.getswitchinterval()` 的默认值是多少？ | 切回自动路由（profile: null），简洁回答 |
| 3 | `@feynmann` 再给我讲讲 GIL | 报错"未知编程导师: @feynmann"（拼写错误的容错行为） |

**观察点**：本场景是显式指令路径，不考察语义判断；第 3 轮验证 `parseMention` 的错误路径，错误信息应友好。

---

## 场景 8：Socrates ↔ Feynman 边界拉扯（压力测试）

| 轮次 | 用户消息 |
|---|---|
| 1 | Python 的引用计数是怎么运作的？为什么光靠它还不够，还得配一套 GC？我想把这里面的逻辑链条完整捋一遍。 |
| 2 | 你这段新名词有点多，我跟不上了。能不能退回来，用我已经熟悉的东西重新说一遍？ |
| 3 | 好，这下顺了。回到刚才那条线：把对象分成三批来管理，这个设计是出于什么考虑？ |

**期望**：socrates → feynman → socrates，三轮三次路由决策，且每次切换都是"直接切目标"。

**观察点**：这是最接近真实使用的摇摆场景，且全程避开 prompt 原文措辞。第 2 轮的"新名词太多 + 想用熟悉的东西重新说"对应 description 中的 Feynman 反选信号（语义而非字样）；第 3 轮"把设计出于什么考虑说清"对应 Socrates 的原理诉求。同时注意 `maxSwitchesPerTurn: 2` 的上限在此不应被触发（每轮只切一次）。

---

## 执行与记录建议

- **运行方式**：`npm run test:agent`（或真实模型 `npm run test:agent:real`）逐段手动输入，重点看 tool 事件流里 `adopt_profile` 的调用序列是否与期望一致。
- **记录维度**：每轮记录 ①是否调用 `adopt_profile` ②切到什么 ③回答里是否泄露 profile 名 ④切换顺序（先切后答 vs 先答后切）。
- **最有诊断价值的三段**：场景 3（过度激活）、场景 4（过度切换）、场景 6（交还不生效）——这三类是路由设计最容易退化的方向。
- **基线对照（可选）**：如需区分"路由本身失效"与"仅语义泛化不足"，可用 profile description 中的原文典型表达（如"太抽象了，听不懂，用大白话讲讲"）跑一组对照；对照通过而本文档用例失败，即说明问题在语义理解而非机制。
